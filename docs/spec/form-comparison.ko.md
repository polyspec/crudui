# 폼 검증

[English](form-comparison.md).

이 계약은 중첩 폼의 HTTP, 브라우저, 영속 저장 검증을 정의합니다. 구현과 검증기는
이 저장소에서 관리합니다. 검증은 커밋 여부와 관계없이 현재 저장소 트리를 대상으로
실행하며 그 트리의 소스 식별자를 기록합니다. 다른 체크아웃의 소스 파일은 읽지 않습니다.

## 정본 예제와 벤치마크 경계

공개 루트는 CRUDUI 전체 기능 정본 예제입니다. 하나의 레코드 흐름
`List → Detail → Form → Save → List refresh`를 보여 줍니다. 목록·상세·링크·폼·검증·submit·
영속 저장 흐름은 CRUDUI가 생성하고 실행합니다. 페이지는 JavaScript reference, PHP,
PHP extension, Go, Rust의 다섯 서버와 HTML, React, Vue, Svelte의 네 클라이언트,
CSR·SSR 선택을 제공합니다.

외부 단계 버튼과 부모 JavaScript의 가짜 단계 상태 라우팅은 계약에 포함하지 않습니다.

`examples/form-comparison/benchmark-console/`는 별도의 검증 화면입니다. 렌더·검증 매트릭스와
벤치마크 조작은 이 디렉터리가 소유합니다. 정본 페이지에는 벤치마크 매트릭스를 넣지
않습니다. `/displays/`는 경로로 제공하지 않습니다.

## 진행, 제한 시간, 범위

이 계약의 모든 명령, 곧 배포와 supervisor의 빌드 주기와 모든 검증 단계에 세 규칙을
적용합니다.

1. **실행 중에 무엇을 하는지 보고합니다.** 시작과 끝만 남기고 기다리는 검사는 없습니다.
   모든 단계는 자기 제한 시간을 포함한 시작 줄, 실행 중 15초마다 경과 시간 줄, 단계
   이름을 붙인 출력, 통과·실패·시간 초과와 소요 시간을 적은 줄을 출력합니다. 빌드
   대상, 브라우저 보고서, 검사 구간 같은 하위 단위도 같은 방식으로 보고합니다.
2. **모든 단계는 측정한 소요 시간에서 정한 자기 제한 시간을 가집니다.** 실행 전체를
   덮는 제한 시간 하나는 금지합니다. 제한 시간에 도달한 단계는 프로세스 그룹과 그룹을
   벗어난 자손까지 프로세스 트리 전체를 정리하고, 실행은 그 단계의 id와 경과 시간과
   함께 실패합니다. 중단된 검사는 `SIGKILL`을 기다리지 않고 `SIGTERM`에 브라우저를
   닫습니다.
3. **검사는 속한 자리에서 실행합니다.** 트리 검증은 배포한 서비스만 다룹니다. 소스
   스위트, Go·Rust 서버 테스트, ordered JSON 테스트는 호스트와 CI가 실행하며, 컨테이너
   안에서 되풀이해도 그 컨테이너의 빌드 산출물은 하나도 검증하지 않습니다. 개발 중에는
   변경한 코드의 테스트만 실행하고 전체 검증은 마지막에 한 번 실행합니다.

## 소스와 환경

비교는 장기 실행 툴체인 컨테이너 하나에서 실행합니다. 저장소는 `/workspace/source`에
읽기 전용으로 마운트하며 이미지에는 저장소 소스가 없습니다. 커밋 여부와 관계없이 소스
변경은 이미지를 다시 빌드하지 않고 실행 중인 서비스에 적용됩니다.

### 툴체인 이미지

`examples/form-comparison/Containerfile`은 이미지 하나를 정의합니다. Node.js 26, Git,
PHP 8.4(CLI, 개발 헤더, mbstring, XML), Composer, C 빌드 도구, Go 1.27, stable Rust,
tini, 고정한 Chromium과 샌드박스를 포함합니다. 어떤 명령도 저장소를 복사하거나 읽지 않으며
저장소에 의존하는 빌드 단계도 없습니다. 이미지 태그는 Containerfile 내용의 SHA-256
digest 앞 16자리이므로 이 파일이 바뀔 때만 이미지를 다시 빌드합니다. 컨테이너는 두 볼륨
루트를 비특권 `node` 사용자에게 넘기기 위해서만 root로 시작하고, 이후 그 사용자로
supervisor를 실행합니다.

프로세스 1은 tini입니다. 빌드, Git 비교, 브라우저 검사는 supervisor가 시작하지 않은
고아 프로세스, 곧 esbuild와 Git과 Chromium과 그 크래시 처리기를 남깁니다. 프로세스 1이
이들을 입양하므로, 회수하지 않는 프로세스 1은 그 전부를 컨테이너가 사는 동안 좀비로
남깁니다. 명령은 하나이므로 런타임이 entrypoint와 command를 어떻게 합치더라도 tini가
프로세스 1입니다.

### 빌드 볼륨

호스트(macOS)와 컨테이너(Linux)의 바이너리가 다르므로 빌드 산출물은 호스트 트리에 두지
않습니다. 컨테이너는 이름 있는 볼륨 두 개를 소유합니다.

- `/workspace/build`: 빌드 트리, npm 의존성과 패키지 빌드, Composer 설치, PHP 확장 빌드,
  Cargo target, Go·Rust 서버 바이너리, 빌드한 프레임 페이지가 있는 공개 디렉터리
- `/workspace/cache`: npm, Composer, Go, Cargo 캐시

`/data`는 저장 레코드를, `/results`는 검증 보고서를 보관합니다. 둘 다 배포 디렉터리입니다.

빌드 트리 `/workspace/build/tree`는 마운트한 저장소에서 Git이 보여 주는 파일, 즉 추적
파일과 무시되지 않은 미추적 파일을 담습니다. npm, PHP 확장 빌더, Cargo·Go 경로 의존성은
소스 옆에 파일을 쓰는데, 읽기 전용 마운트는 이 쓰기를 거부하고 컨테이너 런타임은 디렉터리가
없는 읽기 전용 마운트 안에 볼륨 마운트 지점을 만들지 못하므로 빌드 트리를 둡니다. 호스트의
`node_modules`, `vendor`, 빌드 산출물을 포함한 무시 파일은 복사하지 않습니다. 매니페스트가
복사한 경로를 기록합니다. 저장소에서 제거한 경로는 빌드 트리에서도 제거하며, 매니페스트에
기록되지 않는 빌드 산출물은 유지합니다. supervisor는 해당 체크아웃 디렉터리의 오래된
디렉터리를 다시 만들어 오래된 내용을 제거한 뒤 `polyspec/ordered-json` 모노레포의 고정 리비전 하나를 빌드 트리의
`.form-comparison/sources/ordered-json`에 체크아웃합니다.
다섯 구현 패키지 디렉터리(`go/`, `js/`, `php/`, `php-extension/`, `rust/`)는 그 리비전에
존재해야 하며, 별도 저장소나 submodule이 아닙니다.

### 자연 적용

컨테이너에서는 supervisor `examples/form-comparison/supervisor.mjs` 하나가 실행됩니다.
시작하면 빌드 트리를 동기화하고 모든 대상을 빌드한 뒤 공개 서버와 API 서버 네 개를
시작합니다. macOS 호스트의 파일 이벤트는 VM 파일 공유를 거쳐 Linux 컨테이너에 전달되지
않으므로, supervisor는 마운트한 저장소를 1초마다 Git으로 비교합니다. 비교 대상은 체크아웃
커밋과 커밋하지 않은 모든 경로의 크기·수정 시각입니다. 변경된 경로만 복사하고 입력이 바뀐
대상만 아래 순서로 실행한 뒤 해당 프로세스만 다시 시작합니다. 의존하는 대상이 실행되면 그
대상도 실행합니다.

| 대상 | 입력 | 의존 | 재시작 |
| --- | --- | --- | --- |
| `npm-dependencies` | 루트 `package.json`, `package-lock.json`, 패키지 매니페스트 | | 공개 서버 |
| `javascript-packages` | TypeScript 검증기·생성기 패키지, 루트 `tsconfig` 파일 | `npm-dependencies` | |
| `ordered-json-javascript` | 고정 체크아웃의 `js/` 패키지를 `node_modules/ordered-json`에 복사 | `npm-dependencies` | |
| `frames` | 예제의 `build.mjs`, `public/`, `src/`, `viewer/`, `fixtures/`, TypeScript 패키지, 폼 스냅샷 모듈 | `npm-dependencies`, `ordered-json-javascript` | |
| `browser-matrix` | `src/runtime-paths.json` | | 공개 서버, Go, Rust |
| `public-server` | `server.mjs`, `src/json.mjs` | | 공개 서버 |
| `composer` | `packages/validator-php/`, 생성기 Composer 매니페스트와 lock | | |
| `crudui-php-extension` | `packages/php-ext/`, CRUDUI·공용 확장 빌드 스크립트 | | PHP 확장 |
| `ordered-json-php-extension` | OrderedJSON·공용 확장 빌드 스크립트 | | PHP 확장 |
| `go-server` | `servers/go/`, Go 생성기·검증기 | | Go |
| `rust-server` | `target/`을 제외한 `servers/rust/`, Rust 생성기·검증기 | | Rust |

각 대상은 자기 제한 시간을 선언하고 시작, 실행 중 경과 시간, 완료 소요 시간을 보고합니다.
제한 시간에 도달한 대상은 프로세스 트리를 정리하고 주기를 실패시킵니다. 소스 비교와 고정한
OrderedJSON 체크아웃의 Git 호출도 같은 방식으로 제한합니다. 각 서버의 출력에는 그 서버
이름을 붙입니다. PHP 내장 서버는 요청마다 `Accepted`와 `Closing` 줄을 남겨 다른 모든
메시지를 묻어 버리므로 이 두 줄만 버리고 경고를 포함한 나머지 줄은 모두 남깁니다.

PHP는 요청마다 소스를 읽으므로 PHP 소스 변경은 빌드나 재시작이 필요 없고 설치된 Composer
사본만 교체합니다. `.gitignore`가 바뀌면 트리 전체를 동기화합니다. supervisor 모듈 변경은
기존 컨테이너 안에서 supervisor 프로세스를 다시 로드해 적용하며 모든 볼륨을 유지합니다.

### 소스 식별자

트리의 소스 식별자는 체크아웃 커밋과 커밋하지 않은 변경의 SHA-256 digest입니다. digest는
운영자 로컬 파일인 `.claude/settings.local.json`을 제외하고 `git status`가 보고하는 모든
경로를 정렬한 순서로, 경로와 내용 digest
또는 삭제를 포함합니다. 커밋하지 않은 변경이 없는 트리는 `changes: null`입니다. 식별자
비교는 같은 파일이라도 호스트와 컨테이너에서 다른 inode, device, change time을 사용하지
않습니다.

빌드 주기가 끝나면 supervisor는 식별자를 공개 디렉터리의 `source.json`에 씁니다. PHP, Go,
Rust 서버는 상태·생성·SSR 응답마다 이 파일을 읽고, 메인 페이지와 프레임은 로드할 때 이 파일을
가져옵니다. 어떤 빌드도 커밋을 포함하지 않습니다.

### 빌드 주기

빌드 주기의 상태는 `building`, `ready`, `failed` 중 하나입니다.
supervisor는 다시 빌드하고 재시작한 뒤 API 서버마다 상태 요청을 한 번 보냅니다. 게시한
식별자와, PHP 확장의 경우 빌드하고 로드한 `crudui.so`의 digest를 요구합니다. 공개 서버는
supervisor에게서 상태를 프로세스 메시지로 받습니다. `/api/health`는 ready 주기에서만
`{"status": "ok", "servers": [...]}`를 반환합니다. `/api/source`는 현재 주기가 building이
아니게 되면 주기 번호, 상태, 식별자로 응답합니다. 빌드가 실패하면 이전 프로세스를 계속
실행하고 오류와 함께 `failed`를 보고합니다. 다른 빌드를 선택하지 않습니다.

각 하위 서버는 listen 소켓을 바인딩한 뒤 준비 이벤트를 한 번 게시합니다. supervisor는 이
이벤트를 기다린 뒤 상태를 요청합니다. 시작 절차와 검증은 sleep 간격, 재시도 반복, 주기적
상태 요청을 사용하지 않습니다. 유일한 간격은 위의 소스 비교와 실행 중인 단계의 진행 줄이며,
진행 줄은 경과 시간을 보고할 뿐 준비 여부를 판단하지 않습니다.

호스트 명령은 설치된 패키지 기록 하나에서 컨테이너 실행 파일을 해석합니다. 패키지 기록은
버전이 포함된 설치 디렉터리 하나와 정규 실행 파일 하나를 식별합니다. 상대경로, 심볼릭
링크, 누락된 기록, 일치하는 복수 기록, 대체 명령 공급자를 거부합니다. 실행 경로 결과가
잘못되면 다른 경로를 시도하지 않습니다.

supervisor는 `crudui.so`와 `ordered_json.so`에 공용 PHP 확장 빌더 하나를
사용합니다. 각 확장은 명시적인 빌드 진입점에서 소스, 모듈 이름, 출력 디렉터리, 로드
검사를 선언합니다. 빌더는 `php-config` 실행 파일 하나에서 PHP 실행 파일, 헤더, 빌드
플래그를 읽고 `phpize`, Autoconf, libtool 없이 두 모듈을 직접 컴파일합니다. 컴파일
전에 필요한 각 실행 파일을 한 번 확인합니다. 상대경로, 심볼릭 링크, 누락된 도구, 여러
발견 결과, 서로 다른 PHP 설치 정보가 있으면 빌드에 실패합니다. 명령이 실패한 뒤 다른
실행 파일이나 빌드 경로를 선택하지 않습니다. 생성한 빌드 경로와 모듈 경로에는 정규
파일과 디렉터리만 포함합니다.
Linux 툴체인은 versioned `php-config` 파일을 명시하고 설치된 Debian `gcc` 패키지
기록 하나에서 C 컴파일러를 선택합니다.

폼 비교 CI 작업은 소스·생성기 생성 스위트를 실행하기 전에 루트 npm 그래프와 PHP
검증기·생성기의 Composer 그래프를 설치합니다. 깨끗한 체크아웃은 무시된 `vendor/`
디렉터리를 사용하지 않습니다.

브라우저 검증은 이동 전에 메인 페이지 준비 이벤트를 수신할 호스트 콜백을
등록합니다. 메인 페이지는 초기 비교 프레임 두 개가 준비 이벤트를 게시한 뒤 준비
이벤트를 게시합니다. 검증기는 브라우저 평가 호출을 열린 상태로 유지하지 않고 호스트
콜백을 기다립니다. 공개 디렉터리에 직접 복사하는 모든 모듈은 브라우저가 해석할 수 있는
import만 사용합니다. 소스 검증은 해당 모듈을 HTTP로 제공해 import까지 Chromium에서
로드합니다. 초기화할 수 없는 프레임은 준비 이벤트 대신 이유를 게시하고, 페이지는 그 이유로
실패합니다. 메인 페이지
준비 전에 스크립트 오류, 페이지 실패, 페이지 종료가 발생하면 현재 서버 실행을 실패로
처리하고 오류를 기록합니다. 초기화 실패를 확인한 뒤 준비 대기를 계속하지 않습니다.
검증기는 작업을 시작하기 전에 해당 작업과 렌더러 이벤트도 구독합니다. 결과를 읽기 전에
작업 Promise와 렌더러 완료 신호를 기다립니다. 주기적인 DOM 조회나 경과 시간으로 페이지
준비, 프레임 준비, 검증 완료, 렌더링 완료를 추론하지 않습니다. 진행 게시가 중단된
브라우저 작업은 시간 제한으로 실패할 수 있지만 시간 제한 도달을 성공으로 판정하지
않습니다.

## 구현과 요청

PHP, PHP 확장, Go, Rust는 동일한 컴파일, 렌더링, 검증, 영속 저장, SSR 요청 계약을
구현합니다. 각 서버는 자체 생성기와 검증기를 사용합니다. PHP 확장 프로세스는
`crudui.so`와 `ordered_json.so`를 로드하고 PHP 프로세스는 두 확장을 로드하지
않습니다. 클래스 출처, 모듈 해시 또는 소스 식별자가 다르면 supervisor가 거부합니다.
PHP 프로세스는 빌드 트리의
`packages/generator-php/vendor/composer/installed.php`에서 검증기 설치
디렉터리를 읽습니다. 이 파일은 선택한 생성기 오토로더의 설치 패키지 기록입니다. 다른
Composer 설치가 등록한 기록은 패키지 선택에 영향을 주지 않습니다. 기록 파일, 설치
디렉터리, 검증기 클래스는 심볼릭 링크가 없는 일반 경로를 사용해야 합니다. 검증기
클래스는 빌드 트리의 대응 소스 파일과 일치해야 합니다. 프로세스는 선택한 패키지
기록의 누락 또는 잘못된 형식, 외부 설치 디렉터리, 다른 설치 파일을 거부합니다.
PHP 상태·생성·SSR의 모든 출처 응답은 생성기 소스 디렉터리의 `Generator`와 `Form`,
선택한 Composer 설치 디렉터리의 `Validator`를 보고합니다. 시작 검증과 결과 검증은
하나의 클래스 위치 계약을 사용하며 소스 비교가 통과한 뒤 이 세 위치만 허용합니다.
시작 검증이 상태 응답을 거부하면 실패 메시지는 서버와 이 계약을 충족하지 못한 첫
응답 필드를 명시합니다.

공개 API는 `/api/{server}/{action}/{renderingPath}/{framework}`만 허용합니다. 공개
프로세스는 PHP 프로세스, PHP 확장 프로세스, Go 프로세스, Rust 프로세스를 각각
하나만 시작합니다. 허용한 요청은 선택한 프로세스의
`/api/{action}/{renderingPath}/{framework}`로 전달합니다. API에는 구현 리비전이나
데이터 구조 경로가 없습니다. `bindForm`과 `createForm`은 렌더링·편집 경로를
선택합니다. 키 객체는 반복 인스턴스 데이터를 정의하며 구현이나 URL을 선택하지
않습니다.

`ssr` 동작은 렌더링 경로와 프레임워크 하나의 프레임 문서를 제공합니다. 쿼리는 정확히
`lang`(`ko` 또는 `en`), `server`(응답하는 런타임), `initialization=ssr`이며 각각 한
번씩입니다. 그 밖의 쿼리는 `Expected lang, server and initialization for this SSR frame`로
거부합니다. 서버는 빌드된 프레임 문서
`{public}/frames/{renderingPath}-{framework}/index.html`을 읽습니다. 이 문서에는 `<html>`
시작 태그, 빈 폼 뷰 `<div id="form-view"></div>`, `</body>`가 각각 정확히 하나 있어야
하며, 그 밖의 문서는 `The frame document must contain one html start tag, one empty form
view and one body end tag`로 거부합니다. 응답은 그 문서에 세 가지만 삽입하고 나머지는
그대로 둔 것입니다. html 시작 태그의 언어, 폼 뷰 안에 저장 레코드로 렌더링한 폼, body
종료 태그 바로 앞의 `<script type="application/json" id="crudui-ssr">`에 담은 레코드와
생성기 출처이며, 이 페이로드의 `<`, `>`, `&`는 JSON 이스케이프로 씁니다. 응답은
`text/html; charset=utf-8`과 `Cache-Control: no-store`로 보냅니다.

브라우저는 `bindForm`과 `createForm` 렌더링 경로를 실행합니다. 두 경로는 동일한
같은 소스 트리의 패키지, 같은 keyed 데이터, 같은 전송 계약을 사용합니다. 선택한 서버가
데이터와 독립된 템플릿 하나를 컴파일하고 브라우저가 이 템플릿을 JSON에서
복원합니다. `bindForm` 경로는 템플릿과 현재 데이터로 필드 모델을 계산합니다. 해당
응용 프로그램 컨트롤러는 입력과 행 작업 후 keyed 데이터를 갱신하고 필드를 다시
바인딩합니다. `createForm` 경로는 같은 템플릿으로 편집 폼 세션을 생성하고 데이터
교체와 행 작업에 세션을 사용합니다. 컴파일 실패는 실패로 반환하며 브라우저가 대체
템플릿을 컴파일하지 않습니다.

정본 진입 페이지 `https://crudui.test/`는 서버, 프레임워크, 렌더링 경로를 선택하고 같은 템플릿, 레코드, 언어로
같은 폼의 서버 렌더링과 클라이언트 렌더링을 좌우에 표시합니다. 왼쪽
프레임(`initialization=ssr`)은 선택한 서버(PHP, PHP 확장, Go, Rust)의 프레임 문서입니다.
이 문서는 저장 레코드로 렌더링한 폼과 같은 레코드를 담은 페이로드를 함께 전달하고, 선택한
프레임워크가 같은 템플릿과 데이터로 그 폼을 하이드레이션합니다. 하이드레이션 뒤에도 파싱한
폼 DOM, 즉 자식 순서의 모든 요소, 속성 값, 텍스트는 바뀌지 않아야 합니다. 속성 순서는 DOM의 일부가 아니므로
(React는 input의 `type`, `value`, `name`을 다른 속성 뒤에 설정) 비교하지 않으며, 문자열
렌더러의 바이트 동일 HTML은 생성 검사와 네이티브 생성 검사가 확인합니다. `style` 속성은 CSS 선언 블록이므로 CSS
객체 모델이 직렬화한 선언으로 비교합니다. React는 고정 행의 `--crudui-sticky-depth:0`을
`--crudui-sticky-depth: 0;`으로 씁니다. 비교에서 빼는 것은 프레임워크가 렌더링 기준점으로 두며
아무것도 그리지 않는 노드인 주석(Vue)과 빈 텍스트 노드(Svelte)입니다. 비교 대상은 뷰 컨테이너가
담고 있는 것이며 컨테이너 자체는 아닙니다. 프레임워크는 자신이 사용한 컨테이너에 시작 방식을
기록합니다. Vue는 마운트한 컨테이너에 `data-v-app`을 쓰고 하이드레이션한 컨테이너에는 쓰지
않으며, 이 표시는 아무것도 그리지 않습니다. 해당 열이 실제로 하이드레이션했는지는 아래의 프레임
노드 검사가 강제하며 이 비교가 강제하지 않습니다. 각 어댑터는
하이드레이션이 서버 렌더링 노드를 어떻게 다루는지 선언합니다. React, Vue, HTML 렌더러는
그 노드를 이어받으며 프레임은 모든 노드가 그대로 남았는지 확인합니다. Svelte는 자신의 서버
렌더러가 쓰는 `<!--[-->` 표시가 있는 마크업만 하이드레이션할 수 있고 폼 서버는 그 표시를
쓰지 않으므로, 컨테이너를 비우고 자신의 노드를 마운트합니다. 오른쪽
프레임(`initialization=csr`)은 빌드된 프레임 문서입니다. 저장 레코드를 요청하기 전에
데이터 없이 폼을 마운트하고, 받은 레코드를 기존 폼에 주입합니다. `lang`, `server`,
`initialization` 중 하나라도 없는 프레임 URL은 실패합니다. 프레임은 페이지 스타일시트보다
먼저 `@crudui/generator-core/crudui.css`를 불러오므로 계산된 CSS를 문법 스타일과 함께
비교합니다. 페이지 스타일시트는 `#view` 안을 스타일링하지 않습니다. 각 프레임은 비교 대상
요소 안에서 폼을 `#form-view`에, 브라우저 전용인 구조 맵과 현재 데이터 보기를
`#outline-view`와 `#data-view`에 렌더링합니다. 서버는 폼만 렌더링합니다.

정본 진입 페이지는 `List → Detail → Form → Save → List refresh` 전체 파이프라인을 소유합니다.
벤치마크 진입점은 `/benchmark-console/`이며 매트릭스 검증을 소유합니다. `/displays/` 엔드포인트는
제공하지 않습니다.

정본 페이지의 `initialization`은 폼 문서뿐 아니라 페이지 단계에도 적용합니다.
`initialization=ssr`이면 선택한 서버가 최초 HTTP 문서에 목록 또는 상세 CRUDUI 마크업을
직접 기록하고, 브라우저 JavaScript는 기존 마크업에 동작만 연결하며 단계를 다시 가져오거나
교체하지 않습니다. `initialization=csr`이면 최초 문서에는 셸만 포함하고 브라우저 JavaScript가
선택한 단계 API를 요청해 삽입합니다. 폼 SSR 선택에도 같은 규칙을 적용해 폼 iframe 문서가
서버에서 렌더링됩니다. 따라서 서버 렌더링 페이지의 생성된 목록·상세 마크업은
`view-source`에서 확인할 수 있어야 합니다.

모든 렌더 비교에는 React·Vue·Svelte와 함께 프레임워크 독립 HTML 렌더러가 포함됩니다.
따라서 parity 판정 대상은 네 렌더러입니다.

정본 목록의 열은 의미에 따른 정렬을 사용합니다. 식별자·수치·금액은 우측, 상태는 중앙,
날짜는 중앙, 문자·HTML 값은 좌측, 이미지 셀은 가로·세로 모두 중앙에 배치합니다. 표 셀은
세로 중앙 정렬이며, 목록에는 레코드 식별자를 명시적인 순번 열로 포함합니다. 금액 표시는
원본 값에 없는 후행 0을 추가하지 않습니다.

정본 목록은 45개 레코드를 가지며 offset 방식으로 페이지당 20개를 표시합니다. 따라서
20개·20개·5개를 담은 세 페이지가 존재합니다. 선택한 페이지는 모든 목록 URL에 포함되며,
선택한 서버가 목록을 렌더링하기 전에 적용합니다. public 서버는 모든 네이티브 목록
어댑터에 같은 `page`와 `total` 옵션을 전달하며, 어댑터는 `total`을 현재 페이지의 행 수로
바꾸지 않습니다.

`bindForm` 컨트롤러는 `createForm` 인스턴스와 같은 작업을 지원합니다. 행 작업,
`toggle-row`, `select-row`, `expand-all`, `collapse-all`, `undo`입니다. 접힌 행과
되돌리기 이력을 keyed 데이터와 분리해 generator-core의 뷰 상태·이력 함수로 유지하고, 폼
런타임의 포커스 규칙에 따라 포커스를 옮기거나 유지합니다.

전체 브라우저 행렬은 시나리오 보고서 64개와 초기화 보고서 32개를 포함합니다.

- 서버 4개: PHP, PHP 확장, Go, Rust
- 프레임워크 4개: React, Vue, Svelte, HTML 렌더러
- 렌더링 경로 2개: `bindForm`, `createForm`
- 시나리오 보고서의 전송 2개: 네이티브 multipart 폼, ordered JSON

모든 보고서는 동일한 명세, 컴파일한 템플릿, 데이터, 검사를 사용합니다. 시나리오
검사는 `ssr` 프레임에서 실행합니다. 네이티브
저장과 JSON 저장은 동일한 레코드, 식별자, 부모 식별자, 위치를 생성해야 합니다.
Ordered JSON은 모든 깊이의 객체 멤버 순서를 보존합니다.

## 구조, 데이터, 식별자

구조 컴파일, 인스턴스 데이터, 렌더링, 검증을 분리합니다. 컴파일한 템플릿은 레코드
값을 포함하지 않고 JSON으로 직렬화할 수 있으며 컴파일을 사용할 수 없어진 후에도
재사용합니다. 동일한 캐시 키의 반복 데이터 주입, 편집, 재마운트는 컴파일 요청을
추가하지 않습니다.

반복 컬렉션은 행 식별자를 키로 사용하는 객체입니다. 저장된 sequence는 `__`와
13자리 십진수와 `__`로 구성합니다. 저장 전 신규 행은 `__`와 13자리 소문자
16진수와 `__`로 구성합니다. 키는 부모 컬렉션 안의 행을 식별하며 객체 멤버
순서가 표시 순서를 결정합니다. 런타임은 키 문자열로 저장 여부를 추론하지 않습니다.

전송 데이터에는 숨김 sequence 컨트롤, 보조 식별자 필드, 순서 필드가 없습니다.
서버는 같은 부모 아래 저장된 행에서만 기존 키를 확인합니다. 확인되지 않은 키에는
새 sequence를 할당하고 범위가 명시된 키 변경을 반환합니다. 삭제된 sequence는 다시
사용하지 않습니다.

명시적인 빈 객체는 빈 컬렉션이며 행 컨트롤을 생성하지 않습니다. 컬렉션 데이터가
누락되면 초기 행 하나를 생성합니다. 표시된 빈 컬렉션은 추가 버튼을 제공합니다.
표시 상태 변경은 데이터를 생성, 제거, 전송하지 않습니다. 행이 있는 숨김 컬렉션은
해당 행을 계속 전송합니다.

## 브라우저 검사

각 시나리오 보고서는 다음 동작을 모두 검사합니다.

- 렌더링, 네이티브 이름, 숨김 식별자 컨트롤 0개
- 추가, 복사, 이동, 제거, 저장된 키 교체
- 5, 7, 1 순서의 비연속 저장 식별자
- 숨김 필수 필드를 포함한 클라이언트와 서버 검증
- 네이티브와 JSON 전송, 잘못된 요청 거부, 정확한 재조회
- 빈 회사, 스토어, 부서 컬렉션 전체 동작
- 부모 관계, 형제 식별자 유지, 삭제 ID 미사용
- 캐시 구조 재사용과 컴파일 요청 수 유지

초기화 보고서는 왼쪽 프레임에서 18단계를 실행하고 저장소를 초기화한 뒤 오른쪽
프레임에서 같은 단계를 실행합니다. 두 실행 모두 `copied`부터 `saved-new`까지 행 키
입력을 반복하므로 두 열이 같은 키를 생성합니다. 단계는 다음과 같습니다.

- `mounted`: 저장소를 초기화하고 해당 열의 프레임 문서를 다시 불러 각자의 초기화 경로로
  시작합니다. 서버가 렌더링한 폼을 하이드레이션(왼쪽)하거나 마운트 후 주입(오른쪽)
- `reinjected-1`, `reinjected-2`: 같은 캐시 템플릿으로 저장 레코드를 다시 주입
- `data-hidden`, `data-restored`: 조건 필드를 숨기는 레코드, 그다음 저장 레코드를 주입
- `edited`: 회사 이름, 스토어 이름, 메모를 수정하고 체크박스를 전환
- `saved`: 저장하고 검증 결과, 저장 레코드, 키 변경을 기록
- `reloaded`: 저장 레코드를 다시 조회
- `copied`, `moved`, `copy-removed`, `added`: 버튼으로 회사 행을 복사, 이동, 제거,
  추가하고 추가한 행을 수정
- `saved-new`: 추가한 행을 저장
- `collapsed-all`, `expanded-all`, `undone`: 구조 맵의 모두 접기, 모두 펼치기, 되돌리기
  버튼을 누름
- `empty`, `restored`: 빈 회사 컬렉션, 그다음 저장 레코드를 주입

단계는 키보드 사용자처럼 포커스를 표시해 컨트롤에 포커스합니다(`focus({ focusVisible: true })`).
브라우저는 같은 문서에 포인터 입력이 있었으면 스크립트 포커스를 표시하지 않으므로, 그러지 않으면
비교 전에 한 프레임 안을 클릭한 것만으로 그 열의 CSS만 달라집니다.

두 열은 같은 입력을 받아야 하는데 포인터는 한 프레임 위에만 있을 수 있습니다. 모든 브라우저에서
프레임 안의 `:hover`를 막는 페이지 스타일은 없습니다. Safari에서는 프레임의 `pointer-events: none`도,
프레임을 덮는 요소도 막지 못합니다. 따라서 캡처는 포인터가 두 프레임 밖에 있을 때만 합니다. 포인터가
프레임 위에 있으면(그 문서 요소가 `:hover`와 일치하면) 비교는 결과 없이 멈추고 포인터를 프레임 밖으로
옮긴 뒤 다시 비교하라고 알립니다. 로드 뒤 표시하는 목록도 비교하지 않고 같은 안내를 표시합니다.
페이지 자체는 스크롤하지 않으므로 멈춰 있는 포인터와 프레임의 위치 관계가 바뀌지 않습니다. 컨트롤과
결과는 뷰포트 높이의 45%로 제한한 패널 안에서 스크롤하고, 두 프레임은 나머지를 좌우로 나눠(1000px
이하에서는 위아래 절반) 각자 안에서 스크롤합니다. 따라서 런타임의 포커스 이동은 그 프레임만
스크롤합니다. 스크롤되는 페이지에 프레임을 세로로 쌓았을 때 Safari는 `copied` 단계의 포커스 이동에서
페이지를 0에서 602px로 스크롤해, 페이지 머리글에 멈춰 있던 포인터 아래로 왼쪽 프레임을 가져왔습니다.

오른쪽 각 단계는 저장한 왼쪽 단계와 `formSnapshot`, `styleSnapshot`,
`compareSnapshots`로 비교합니다. 비교 대상은 모든 속성을 포함한 파싱 DOM, 현재 컨트롤
상태, 네이티브 필드, 요소와 의사 요소의 계산된 CSS, ordered JSON 데이터, 포커스와 텍스트
선택 범위, 저장 응답입니다. 직렬화한 HTML은 비교하지 않습니다. 속성 순서는 DOM의 일부가
아니고, 브라우저 엔진은 프레임워크가 설정하는 속성을 서로 다른 순서로 만듭니다(Safari와
Chromium은 복원된 Vue checkbox의 `checked`와 `value` 순서가 다름). 각 열의 재주입·복원
단계는 그 열의 `mounted` 단계와도 비교합니다. 아무것도 제거, 교체, 정규화하지 않습니다.
보고서는 일곱 범주의 비교 24개, 결과 168개입니다.

페이지는 두 프레임을 모두 표시합니다. 두 프레임이 로드되면 상단 목록이 `mounted`
상태를 비교하고, 비교 버튼과 전체 검사는 단계가 끝날 때마다 결과를 추가합니다.
보고서는 단계마다 HTML, DOM, 컨트롤 상태, 필드, 데이터, 포커스, 응답, CSS digest와
실패한 CSS 비교의 기대·실제 CSS를 보존합니다.

두 프레임과 페이지, 같은 origin의 다른 모든 탭은 같은 저장 레코드를 읽고 교체합니다.
페이지에서 시작한 작업(프레임 버튼이나 폼 제출, 비교 버튼, 전체 검사)은 origin 잠금
하나(`navigator.locks`)를 가진 동안에만 레코드를 변경합니다. 다른 작업이 잠금을 가진 동안
시작한 작업은 실행되지 않고 다른 검사나 저장이 실행 중이라고 알립니다. 전체 검사나 검증기가
직접 호출하는 검사는 이미 잠금을 가진 작업 안에서 실행됩니다. 잠금은 브라우저 하나에 속합니다. 같은
배포를 쓰는 다른 브라우저, 다른 사람, 자동화 실행은 잠금 없이 같은 레코드를 읽고 교체하므로, 서로 다른
브라우저의 검사를 동시에 실행하면 안 됩니다.

포인터와 키보드 검사는 행 추가 후 포커스가 새 행의 첫 입력으로 이동하고, 그 입력이
프레임 뷰포트와 메인 페이지 뷰포트 안에 모두 보이는지 확인합니다. 프레임과 페이지는
필요한 만큼만 스크롤합니다. 프레임 문서 검사는 모든 렌더링 경로와 프레임워크의 초기화
문서 두 개를 확인합니다. CSR 문서는 뷰가 비어 있고 페이로드가 없는 빌드 문서 그대로여야
하고, SSR 문서는 같은 문서에 세 가지 삽입만 적용한 것이어야 하며, 네 서버 문서 뒤의 빌드
문서를 SHA-256으로 비교합니다. 생성 검사는 모든 서버와 프레임워크의 한국어·영어 SSR
출력을 확인하고, 모든 서버가 같은 잘못된 SSR 쿼리를 같은 메시지로 거부하는지 확인합니다.

## 실행기와 보고서

브라우저는 작업을 시작하고 호스트는 짧은 프로토콜 호출로 상태와 완료 보고서를
수집합니다. 장시간 행렬 전체를 하나의 DevTools 프로토콜 호출에서 실행하지 않습니다.
수집기는 현재 보고서, 보고서 시작 시각, 완료 보고서 수, 요청·응답 수, 마지막
요청·응답 시각을 기록합니다.

서버 실행의 각 단위는 측정한 소요 시간에서 정한 자기 제한 시간을 가지며, 실행 전체를
덮는 제한 시간은 없습니다. 27~30초로 측정한 초기화 보고서는 180,000밀리초, 1~2초로
측정한 시나리오 보고서는 60,000밀리초, 두 보고서 사이의 페이지 작업은 120,000밀리초를
가집니다. 보고서 작업을 둘러싼 구간도 자기 제한 시간을 가집니다. 메인 페이지는
180,000밀리초, 상호작용 검사는 300,000밀리초, 산출물 기록은 300,000밀리초입니다. 수집기는
단위가 실행되는 동안 15초마다 이름과 경과 시간을 출력하고, 완료된 보고서마다 결과와 소요
시간을 출력합니다. 제한 시간에 도달한 단위는 그 단위 이름과 경과 시간과 함께 실행을
실패시키며, 실패는 현재 상태와 완료된 모든 보고서를 보존합니다.

완료된 서버 보고서는 보고서 24개의 브라우저 작업을 요구합니다. 검사 19개씩의
시나리오 보고서 16개와 비교 결과 168개씩의 초기화 보고서 8개입니다. 또한 상호작용 검사
80개, `csr` 프레임의 로드 전 마운트 검사 8개, 프레임 문서 검사 16개, 브라우저·페이지
오류 0개, 보고서와 모든 시나리오·초기화 보고서가 공유하는 하나의 소스 식별자,
900,000밀리초 이내의 실행 시간을 요구합니다. `passed` 필드는 boolean이어야 합니다. 실행 활동, 초기화 단계, 시간
증거가 누락되면 보고서는 미완료입니다.

네 서버 집계는 서버마다 완료된 보고서 하나를 요구합니다. 시나리오 검사 1,216개,
초기화 비교 5,376개, 상호작용 검사 320개, 마운트 검사 32개, 프레임 문서 검사 64개가 모두
성공해야 하며, 네 서버 문서 뒤의 빌드 문서가 같고 성능 결과 4개가 모두 성공해야 합니다. 실패, 누락,
잘못된 형식, 불일치가 하나라도 있으면 `passed: false`와 종료 상태 1을 반환합니다.
실패가 0개인 완전한 집계만 종료 상태 0을 반환합니다.

## 추가 검증

생성 검증은 성공 결과 450개, HTTP 요청 899개, 서버·렌더링 경로·프레임워크 조합
32개를 요구합니다. 저장소 검증은 원자적 갱신, 잠금, 위치 기반 조회, 부모 관계,
파일 변경 없는 요청 거부, 전체 삭제, sequence 할당을 확인합니다. 타입 검증은 모든
서버에서 동일한 스칼라와 컬렉션 규칙을 확인합니다.

PHP 경고 두 종류는 이 검사들에 속하며 결함이 아닙니다. 저장 검사의 `request-size-limit`은
2 MiB 요청 한도를 넘는 필드를 세 전송 방식으로 보내고 상태 413을 요구하므로 `POST
Content-Length ... exceeds the limit` 경고를 남깁니다. 브라우저 `shape` 검사는
`max_input_vars`를 넘는 필드 10,001개의 네이티브 폼을 보내고 상태 400을 요구하므로 `Input
variables exceeded 10000` 경고를 남깁니다. 각 경고는 해당 검사가 단언하는 요청에서
나옵니다.

빠른 소스 검사는 보고서 정책 실패, 프로토콜 시간 제한 동작, 보고서별 제한 시간과 진행
보고, 단계 실행기의 제한 시간과 프로세스 트리 정리, 버리는 PHP 접근 로그 줄, 소스 식별자와
빌드 대상 선택, 빌드 트리 동기화, 스냅샷 차이, 생성 캐시 동작, 요청 수 변경을 재현합니다. 이 검사는 트리 검증을 대체하지 않습니다. Pull request와 `main` push
CI는 `npm run test:form-comparison`을 실행하며 보고서 정책, 브라우저 작업, 소스 트리와
생성 성능 회귀가 있으면 통합을 실패로 처리합니다.

## 트리 검증

검증은 실행 중인 비교 컨테이너 안에서 `node` 사용자로 Chromium 샌드박스를 활성화한 채
현재 트리의 빌드를 대상으로 실행합니다. `/api/source`로 현재 빌드 주기를 최대
600,000밀리초까지 기다리고 ready를 요구합니다. `/results`를 비우고 식별자를
`results/source.json`에 기록한 뒤 다음 단계를 순서대로 실행하며 실패한 단계가 있는 첫
단계에서 멈춥니다.

1. 이 컨테이너가 빌드한 `crudui.so`와 `ordered_json.so`를 로드하는 PHP 처리 모드
   (60,000밀리초, 1초로 측정)
2. 실행 중인 네 서버를 대상으로 하는 생성 검사(120,000밀리초, 7초로 측정)
3. 실행 중인 네 서버를 대상으로 하는 저장 검사(60,000밀리초, 2초로 측정)
4. PHP, PHP 확장, Go, Rust 브라우저 검증 네 개를 동시에(각 1,200,000밀리초, 하나를
   284초로 측정)
5. 이번 실행의 브라우저 보고서 네 개를 집계(120,000밀리초)

각 단계는 배포한 빌드, 곧 이 컨테이너가 컴파일한 확장이나 실행 중인 서버나 빌드한 프레임
페이지를 검증합니다. 소스 스위트, Go·Rust 서버 테스트, ordered JSON 테스트는 이 컨테이너의
빌드 산출물을 읽지 않으므로 호스트와 CI가 맡고 검증은 되풀이하지 않습니다.

브라우저 검사 네 개를 동시에 실행하는 이유는 각 검사가 자기 브라우저 프로세스에서 자기
포커스, 선택, 스크롤을 측정하고 자기 서버와 자기 저장 레코드를 사용하므로 한 검사의 측정이
다른 검사에 닿지 않기 때문입니다. 대신 프로세서가 필요합니다. 검사 하나가 프로세서 약
하나를 사용하므로 배포는 컨테이너에 여덟 개를 줍니다.

이후 같은 빌드 주기와 식별자를 요구합니다. 검증 중에 소스가 바뀌면 실행이 실패합니다. 모든
보고서는 식별자를 기록합니다. 근거 검사는 생성 보고서, 저장 보고서, 브라우저 집계가 그
식별자를 명시하고 이 계약의 모든 개수와 성공 조건을 충족하도록 요구합니다. 호스트 명령은 실행
전과 후 모두 근거의 식별자가 체크아웃의 식별자와 같아야 합니다. 근거에는 이미지 digest나
아카이브 해시가 없습니다. 검증은 배포를 대상으로 하는 다른 자동화 실행과 마찬가지로 배포의
`/data`를 사용하므로 다른 브라우저의 검사를 동시에 실행하지 않습니다.

## 배포

`crudui.test`의 로컬 비교 서비스는 장기 실행 툴체인 컨테이너입니다. 배포 명령은 현재
Containerfile 내용의 태그를 가진 이미지가 없을 때만 툴체인 이미지를 빌드합니다. 이어서
`.form-comparison/deployment/compose.yaml`에 다음을 씁니다.

- 해당 이미지
- `/workspace/source`에 읽기 전용으로 마운트한 저장소 루트
- `/workspace/build`의 `crudui-comparison-build`, `/workspace/cache`의
  `crudui-comparison-cache` 이름 있는 볼륨
- `/data`의 배포 `data` 디렉터리와 `/results`의 `results` 디렉터리
- `containerctl.domain: crudui.test` 레이블

이 정의는 동시에 실행하는 브라우저 검사 네 개에 필요한 프로세서 여덟 개와 8 GB를 서비스에
줍니다. 정의에는 커밋, 아카이브, 이미지 digest가 없으므로 소스 변경이 정의를 바꾸지 않습니다.

상태 검사는 `/api/health`가 모든 서버를 보고할 때만 서비스를 수락합니다. containerctl은 상태
검사 기간마다 최대 10분, 재시도 1 이상 100 이하를 허용하고, 시작 기간에 재시도 횟수와
간격·제한 시간의 곱을 더한 시간, 합계 최대 30분까지 기다립니다. 정의는 그 한도를 사용하지
않습니다. 빈 볼륨의 첫 시작이 모든 것을 설치하고 빌드한 뒤 컨테이너 시작 58초 뒤에 상태를
응답했으므로, 검사는 시작 기간 120초 뒤 5초마다 제한 시간 5초로 24회, 합계 6분을 기다립니다.

containerctl이 기다리는 동안 대기는 조용하지 않습니다. containerctl은 시작한 컨테이너와 각
상태 검사 시도를 경과 시간과 함께 보고하고, 배포 명령은 컨테이너 시작 시점부터 supervisor의
빌드 진행, 곧 각 빌드 대상의 시작과 실행 중 경과 시간과 소요 시간을 출력합니다. 정의 적용은
상태 검사 한도에 containerctl 자체를 위한 1분을 더한 자기 제한 시간을, 이미지 빌드는 자기
제한 시간을 가집니다.

정의를 적용하기 전에 명령은 실행 중인 서비스의 저장 레코드를 내용이 다른 파일을 덮어쓰지
않고 `.form-comparison/deployment/data`에 보존합니다. containerctl로 정의를 적용한 뒤
명시적인 containerctl CA로 HTTPS 홈 페이지, 상태 응답, `source.json`, 저장 데이터 응답을
요청합니다. 라우트, 인증서, 이미지, 마운트, 저장 파일, 컨테이너가 마운트한 저장소에 쓸 수
없다는 것, 제공하는 식별자가 체크아웃의 식별자와 같다는 것을 검사합니다. 재사용 조건을
만족하면 정의를 다시 적용하지 않고 컨테이너 ID, 생성·시작 시각, 이미지, 마운트, 라우트, 인증서,
식별자, 저장 파일, 응답 바이트를 유지합니다. 값이 변경되거나 요청이 실패하면 배포
검증은 실패합니다. `/data`와 빌드 볼륨은 적용 사이에 유지합니다.

배포 검증이 성공하면 명령은 어떤 컨테이너도 사용하지 않는 비교 이미지와, 제거한 아카이브
절차의 커밋별 이미지를 제거하고 더 이상 쓰지 않는 `.form-comparison/candidates`,
`.form-comparison/sources`, `.form-comparison/results` 디렉터리를 제거합니다. 이미지,
Compose digest, 데이터 보존 결과와 두 스냅샷은
`.form-comparison/deployment/verification.json`에 기록합니다.
## 배포 수명주기 불변식

실행 중인 컨테이너가 기대 이미지와 source, build, cache, data, results의 정확한 마운트를
가지면 재사용합니다. 소스 동기화는 `containerctl down`, 컨테이너 재생성, 서비스 restart,
볼륨 재연결을 수행하지 않습니다. `containerctl up`은 컨테이너가 없거나 호환되지 않을 때만
bootstrap에 사용합니다. public pipeline은 목록·상세 표시 요청을 선택된 네이티브 서버로
전달하며 Node 렌더러로 대체하지 않습니다.
